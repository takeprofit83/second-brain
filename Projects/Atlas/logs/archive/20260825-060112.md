# Конспект: VK-бот сообщества на vkbottle — грабли настройки и хардненинга (проект «Дача»)

Конспект для передачи контекста другой модели/агенту без доступа к исходной переписке. Тема не связана с самим Atlas: это техническая справка, вынесенная из другого проекта («Дача» — ESP32-автоматизация дачи, VPS-бэкенд), потому что материал общего назначения — пригодится в любой будущей задаче «поднять/отладить VK-бота сообщества». Написано как справочник (симптом → причина → фикс), не как рассказ о ходе работы.

## Контекст платформы

- Стек: **vkbottle** (асинхронный Python-фреймворк для VK API), `Bot(token=...)`, приём апдейтов через **long polling** — `bot.run_forever()`. Публичный webhook не нужен.
- Бот живёт **внутри сообщества (группы) VK**, не как отдельный VK-аккаунт. Пользователи пишут ему через страницу сообщества, кнопка «Написать сообщение» — не через поиск юзернейма бота, как в Telegram (в VK у сообщений сообщества нет аналога `@botname`).

## Грабли по порядку, в котором на них натыкаешься

### 1. Токену нужен отдельный scope «Управление сообществом»

Токена с правом только «Сообщения сообщества» недостаточно. Без права **«Управление сообществом»** вызов `groups.getLongPollServer` падает с VK error 15 / subcode 1133: `"access denied... cannot be called with current scopes"`.

Приватность сообщества (открытое/закрытое) тут ни при чём — это не причина ошибки, проверять её при отладке этой конкретной ошибки не имеет смысла (потрачено время впустую на проверку).

### 2. Отправка сообщений требует отдельного тумблера, даже когда Long Poll уже работает

Путь в интерфейсе VK: **Управление сообществом → Сообщения → Настройки для бота → «Возможности ботов»**.

Без включения этого тумблера любая отправка падает с `VKAPIError_912: "This is a chat bot feature, change this status in settings"` — даже если Long Poll и получение апдейтов уже настроены и работают.

### 3. Как узнать числовой user_id владельца для allowlist

В VK нет аналога Telegram `/start` → BotFather, который сразу показывает твой numeric id. Практический способ:
1. Задеплоить бота с временным placeholder-id в allowlist.
2. Один раз написать боту `/start`.
3. Прочитать реальный id из лога вида `"Unauthorized /start from user_id=..."` (бот должен логировать такие попытки — если не логирует, добавить логирование именно для этого шага).
4. Подставить реальный id в конфиг/allowlist, передеплоить.

### 4. Лимит длины label у inline-кнопки — 40 символов (VKAPIError_911)

Самая коварная в отладке ошибка: превышение лимита ломает **только шаг обновления клавиатуры** (`event.edit_message(...)`), который идёт ПОСЛЕ того, как основное действие (например, POST команды на бэкенд) уже успешно выполнилось. В результате пользователь видит «кнопка ничего не делает» / «всё сломано», хотя команда реально отработала — сломался только последующий рефреш UI.

Легко ошибочно диагностировать как «нет доступа к серверу» или «команда не дошла», хотя команда дошла нормально, а упал только followup-апдейт клавиатуры.

Фикс — обрезать любой динамический label кнопки до ≤40 символов с многоточием ДО построения `Callback`-кнопки:

```python
def _vk_button_label(text: str, limit: int = 40) -> str:
    return text if len(text) <= limit else text[: limit - 1] + "…"
```

В Telegram такого лимита нет — этот класс багов специфичен для VK и не проявится при портировании бота с Telegram, если явно не следить за длиной label.

### 5. Label тумблер-кнопки должен отражать текущее состояние, а не быть статичным

Статичный generic label (например, «🌦 Погода: вкл/выкл») не даёт видимой обратной связи при нажатии, даже если тап сработал и состояние на сервере реально изменилось. В реальном тестировании это выглядело как мёртвая/сломанная кнопка для пользователя, хотя серверная логика работала корректно.

Фикс: сам label должен отражать текущее состояние (например, «🌦 Погода: учитывается ✅» vs «☀️ Погода: не учитывается»), плюс на каждый тап, меняющий состояние, дополнительно показывать snackbar/toast-подтверждение (`event.show_snackbar(...)`).

Это общее UX-правило для inline-клавиатур (VK и Telegram одинаково), не специфика vkbottle — просто найдено и подтверждено именно на этом VK-боте.

### 6. Косметические баги/warning'и библиотеки (vkbottle 4.10.0)

- При использовании `@bot.loop_wrapper.interval(seconds=N)` при старте печатается `LoopWrapper is deprecated` (рекомендует `vkbottle.interval` / `bot.on_startup`). Безвредно, бот работает нормально — мигрировать не стоит, если только не делается более крупный рефакторинг по другим причинам.
- Внутренний баг логирования (`StyleAdapter has no attribute opt`) — при возникновении какой-то ДРУГОЙ, не связанной с этим, ошибки VK API выводит уродливый traceback. Чисто косметика, на доставленную функциональность не влияет.

### 7. Порядок регистрации хендлеров важен для текстового роутинга

`@bot.on.private_message(text=...)` в vkbottle матчатся **в порядке регистрации** (сверху вниз по файлу), выигрывает первый подошедший. Catch-all-хендлер `@bot.on.private_message()` без `text=` фильтра ДОЛЖЕН регистрироваться ПОСЛЕДНИМ, после всех хендлеров с конкретным текстом (`/start`, `/status` и т.п.) — иначе он перехватит сообщения, предназначенные для них.

Актуально при добавлении в кнопочного бота любого шага со свободным текстовым вводом (например, «введите значение сейчас»).

### 8. Payload-based роутинг callback-кнопок

В VK inline `Callback`-кнопки несут JSON `payload` (словарь), в отличие от плоской строки `callback_data` в Telegram. Это естественный способ роутить многошаговые wizard/flow UI — например `payload={"cmd": "sched_field", "field": "weather"}` — гораздо чище, чем парсинг строки через двоеточие, как только у флоу больше 2-3 веток.

### 9. Не строить full-replace запись конфига на потенциально деградировавшем кэш-чтении

Не специфично для VK, но найдено именно при разработке фичи редактирования расписания в этом VK-боте: если бот забирает upstream-конфиг и при временном сбое чтения молча откатывается на `{}` (или частичный объект), а затем этот `{}`/подмножество используется как база для «сохранить всё» PUT/POST на endpoint с full-replace семантикой (не merge) — можно молча стереть всё, что не было перечитано.

Обязательная защита: перед использованием полученного объекта как базы для full-replace записи проверять, что в нём реально присутствуют ожидаемые ключи; при отсутствии — бросать исключение/прерывать операцию, а не молча писать поверх деградировавшим/частичным состоянием.

### 10. Паттерн деплоя (контекст, не VK-специфика, но полезно для будущих деплоев ботов)

Git-based деплоя на целевом сервере нет — `bot.py` / `Dockerfile` / `docker-compose.yml` / `requirements.txt` лежат плоскими файлами в `/opt/apps/<bot-name>/` на VPS, обновление — через `scp` изменённых файлов, затем `docker compose up -d --build` в этой директории.

`.env` содержит `VK_TOKEN`, `ALLOWED_USER_ID`, `ADMIN_TOKEN`, `BACKEND_URL` (указывает на внутренний Docker-network hostname, не публичный URL) — бот и его бэкенд сидят в общей приватной Docker-сети `apps`, поэтому публичной экспозиции backend API не требуется.

## Итоговая шпаргалка для будущей отладки VK-бота с нуля

| Симптом | Причина | Где искать |
|---|---|---|
| `groups.getLongPollServer` падает, error 15/1133 | не хватает scope «Управление сообществом» у токена | права токена, не приватность сообщества |
| Любая отправка падает `VKAPIError_912` | не включены «Возможности ботов» | Управление сообществом → Сообщения → Настройки для бота |
| Команда вроде выполнилась, но UI/кнопка выглядит сломанной | `VKAPIError_911`, label кнопки >40 символов, упал только `edit_message` после успешного действия | обрезать label до ≤40 символов |
| Тумблер «не реагирует» на тап, хотя состояние меняется | статичный label без отражения состояния | делать label динамическим + snackbar |
| Не тот хендлер обрабатывает сообщение | catch-all зарегистрирован раньше специфичных `text=`-хендлеров | порядок регистрации хендлеров |
| Конфиг после сбоя чтения тихо стал `{}`, full-replace запись стёрла данные | нет валидации наличия ожидаемых ключей перед full-replace записью | добавить guard/raise при неполном объекте |
