# Atlas — конвейер ролей моделей

## Контекст

Atlas — не самостоятельный проект, а часть более крупной архитектуры "Второй мозг" (цифровая копия знаний). Изначально Atlas задумывался для объединения диалогов с разными ИИ-агентами и чатами в единую базу, чтобы можно было бесшовно передавать контекст между моделями.

## Идея бесшовной передачи контекста

1. Диалог ведётся в чате одной модели (например, Gemini).
2. Автоматизация отслеживает реперные точки разговора — поворотные моменты, решения, новые сущности.
3. Система конспектирует весь диалог и сохраняет пометки + саммари в базу.
4. При переходе в чат с другой моделью (например, Qwen) система подгружает конспект и пометки из базы и передаёт их новой модели.
5. Новая модель сразу подхватывает контекст без повторного объяснения.

**Техническая развилка:** для веб-чатов (Gemini, Qwen через браузер) нужен либо парсинг DOM через браузерную автоматизацию, либо ручной экспорт диалога в n8n через отдельный триггер (например, Telegram-бот).

## Роли моделей в конвейере

Изначальная задумка — распределить роли по сильным сторонам моделей:

- **GPT — архитектор.** Ставит задачу, планирует, удерживает общую картину.
- **Клод — программист.** Пишет workflow и код, следит за структурой и целостностью системы.
- **Qwen — рабочая лошадка.** Обрабатывает большой объём рутинных задач (дёшево и быстро за счёт открытых моделей).

## Утверждённая архитектура конвейера

Финальная схема, собранная из четырёх идей:

```
GPT-архитектор → Клод-программист → Qwen-рабочая лошадка → Арбитр → База знаний
        ↑                                                              │
        └──────────────────── рефлексия в контекст ───────────────────┘
```

1. **Конвейер с проверками** — каждая модель передаёт результат следующей, а не работает изолированно.
2. **Роль арбитра** — разрешает конфликты, если, например, GPT и Клод предлагают разные архитектурные решения. Похожая идея есть у сервиса ИИШКА в функции "дебаты 30 моделей" (голосование/синтез).
3. **Нагрузка Qwen объёмом** — раз это самая дешёвая модель по токенам, на неё ложится не только рутина, но и обработка больших объёмов данных.
4. **Рефлексия в базу знаний** — каждая модель после задачи оставляет не только результат, но и краткую рефлексию (что сработало, что нет). База со временем становится живым описанием того, как ставить задачи каждой модели.

## Следующий практический шаг

Спроектировать конвейер как последовательность конкретных n8n-нод: кто кому что передаёт, в каком формате, и где происходит рефлексия. Начать стоит с самого нетривиального узла — детекции реперных точек диалога (промпт-инжиниринг для решения "это поворотный момент или нет").
