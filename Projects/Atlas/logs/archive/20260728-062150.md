## Key operational gotchas learned this session (also in `Atlas_Technical_Documentation.md` §31 and memory `feedback_classifier_blocks_prod_writes`)

- Claude Code's own safety classifier blocks the agent from directly PUTting to n8n's API or writing files to a remote server over SSH (`ssh ... "cat > file"`) — hard block, not a permission prompt, no retry workaround. Read-only equivalents (GET, `cat file`, `grep`) work fine. Practical pattern: prepare the exact script/command, hand it to the user to run themselves in their own PowerShell.
- n8n public API's `PUT /workflows/{id}` `settings` schema is stricter than what `GET` returns — round-tripping `binaryMode`/`availableInMCP` verbatim causes `400 request/body/settings must NOT have additional properties`. Fix: strip to just `{"executionOrder": "v1"}`.
- Windows PowerShell 5.1 misreads literal Cyrillic in a `.ps1` file without a BOM (parser errors mid-string). Fix: encode Cyrillic as base64 in the script, decode at runtime with `[System.Text.Encoding]::UTF8.GetString([Convert]::FromBase64String(...))`.
- Default PowerShell execution policy blocks running local `.ps1` files at all — use `powershell -ExecutionPolicy Bypass -File ...` per-invocation (no system-wide policy change).
- **PowerShell piping text to an external process (e.g. `... | ssh host "cat > file"`) re-encodes using the console's codepage, not the source encoding** — this silently corrupts non-ASCII content even when the source file was read correctly as UTF-8. For any non-ASCII payload being piped to an external process, use a base64 round-trip (`ToBase64String` locally, `base64 -d` remotely) instead of raw text piping.
- n8n API keys: created ad hoc via Settings → n8n API in the UI, used once, deleted immediately by the user — by design never shared back into chat/memory (user's own security practice, reinforced this session after a "masked key" copy-paste confusion).
