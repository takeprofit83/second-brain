# Architecture Decisions Log (ADR-lite)

Краткий индекс архитектурных решений проекта Second Brain + Atlas: что решено и почему. Полная техническая деталь каждого решения — в `Projects/Atlas/Atlas_Technical_Documentation.md` (см. номер секции §N в скобках); здесь — только суть и обоснование, для быстрого поиска "почему сделано именно так" без чтения всей истории.

---

## ADR-001: Adapter Architecture

**Решение:** workflow никогда не вызывает AI-провайдера напрямую. Всегда через отдельный Adapter Core (`Atlas-Kie Adapter Core`, `Atlas-OpenRouter Adapter Core`, ...), у всех — одинаковый контракт: оркестратор передаёт только `provider`, `system_prompt`, `user_input`; выбор конкретного адаптера делает Router.

**Почему:** провайдеров планировалось несколько (Kie, OpenRouter, OpenAI, Claude), и без единого контракта каждая замена/добавление провайдера требовала бы переписывать workflow заново. Адаптер изолирует специфику конкретного API (авторизация, формат запроса/ответа) от остальной системы.

## ADR-002: Docs Sync через n8n-webhook, а не ручной git push (§20)

**Решение:** обновления `Atlas_Project_Log.md` / `Atlas_Technical_Documentation.md` идут через выделенный webhook `atlas-docs-sync` (workflow `Atlas - Docs Sync`), а не через ручной `git commit/push` внутри конкретной агентской сессии.

**Почему:** персистентность — свойство самого Atlas, а не конкретного coding-агента (Claude Code сегодня, что-то другое завтра). Если полагаться на то, что каждый агент не забудет закоммитить, документация рано или поздно разойдётся с реальным состоянием.

---

## ADR-003: Relay-страница на отдельном VPS (§24)

**Решение:** страница-посредник для capture-букмарклетов размещена на отдельном мини-VPS (`tangerine-vps`), не на основном VPS Atlas.

**Почему:** основной VPS отдаёт `Content-Security-Policy: sandbox` через reverse proxy (Nginx Proxy Manager), что превращает любую страницу за ним в опаковый sandboxed-origin — даже `fetch()` к самому себе считается cross-origin и блокируется. Отдельный VPS с голым nginx без прокси и без CSP-заголовков решает проблему без необходимости переделывать основной прокси.

## ADR-004: Chunking / map-reduce для длинных переписок (§26)

**Решение:** длинные переписки режутся на части (`Chunk Input`), каждая обрабатывается отдельным вызовом адаптера, затем собираются обратно (`Combine Chunks`) в единый конспект.

**Почему:** цельная переписка может превышать лимит контекста/токенов провайдера. Map-reduce обходит это ограничение ценой дополнительных вызовов API.

---

## ADR-005: Редактирование секретов в конспектах (§30)

**Решение:** системный промпт конспектирования (во всех трёх местах — основной + оба map-reduce чанк-промпта) требует заменять пароли/ключи/токены на `[REDACTED]`, а не воспроизводить дословно.

**Почему:** реальный инцидент 2026-07-28 — автозахваченный конспект унёс в публичный репозиторий боевые пароли PostgreSQL и MinIO, потому что промпт до этого прямо требовал сохранять "конкретные значения конфигурации" без оговорок про секреты.

## ADR-006: Поле `project` со значением по умолчанию `"atlas"` (§31)

**Решение:** новое поле `project` ("atlas"|"courses"), определяющее путь коммита конспекта (`Courses/` vs `Projects/Atlas/logs/`), по умолчанию равно `"atlas"`, если явно не передано другое.

**Почему:** обратная совместимость — старые букмарклеты/скрипты, ещё не обновлённые под новое поле, должны продолжать работать ровно как раньше, а не ломаться или требовать одновременного обновления всех интеграций.

---

## ADR-007: Конспекты Claude Code сессий — прямой git push, а не через webhook

**Решение:** в отличие от захватов из ChatGPT/Qwen/DeepSeek/Gemini (сырой текст → LLM-обработка через webhook), конспект сессии Claude Code пишется агентом напрямую и коммитится через обычный git, без прогона через `atlas-capture`.

**Почему:** у coding-агента уже есть полный контекст диалога в момент написания конспекта — прогонять его ещё раз через LLM-webhook избыточно, конспект и так уже "готовый".

---

## ADR-008: Параметризация `model`, а не отдельный адаптер под каждую модель (§32)

**Решение:** вместо отдельного `Atlas-Claude Adapter Core` — `model` стал обычным параметром вызова в `Atlas-OpenRouter Adapter Core` (и унаследовавшем его `Atlas-Polza Adapter Core`), с дефолтом на прежнюю модель, если параметр не передан.

**Почему:** и OpenRouter, и Polza дают доступ к любой модели через один и тот же аккаунт/API — значит адаптер соответствует агрегатору (ADR-001), а не конкретной модели. Плодить копию воркфлоу ради смены одной строки `"model"` нарушало бы собственный принцип проекта "не дублировать" (`PROJECT_PRINCIPLES.md`).

## ADR-009: Polza.ai как второй агрегатор рядом с OpenRouter (§32)

**Решение:** добавлен `Atlas-Polza Adapter Core` — копия параметризованного OpenRouter-адаптера с другим URL (`api.polza.ai`) и Bearer-credential.

**Почему:** OpenRouter требует иностранную карту/крипту для оплаты; Polza принимает рубли без комиссий и покрывает те же 400+ моделей через идентичный OpenAI-совместимый формат — снижает зависимость от одного способа оплаты для физлица из РФ. Выбор именно Polza (а не BotHub/RouterAI/Gen-API) — предпочтение пользователя после сравнения агрегаторов.

## ADR-010: Atlas - Model Relay — фиксированная цепочка из 6 узлов, а не цикл (§33)

**Решение:** автоматический обмен репликами между GPT и Claude сделан как линейная цепочка из 6 последовательных вызовов адаптера (3 раунда), а не через n8n Loop Over Items с настраиваемым числом раундов.

**Почему:** циклы в n8n требуют аккуратной передачи накопленного состояния между итерациями — после многочасовой борьбы с UI `Execute Workflow` в этой же сессии решили не рисковать ещё одной сложной конструкцией ради небольшого выигрыша в гибкости. Если понадобится настраиваемое число раундов — переделать в реальный цикл тогда, не заранее.

## ADR-011: `Debates/` как отдельная папка, не `Courses/`/`Projects/Atlas/logs/` (§33)

**Решение:** результат авто-диалога моделей сохраняется в новую папку `Debates/`, а не переиспользует существующие.

**Почему:** это принципиально другой тип артефакта — не захваченная переписка человека с моделью (как в `Courses/`/`Projects/Atlas/logs/`), а результат полностью автоматического обмена между двумя моделями. Смешивание в одну папку затруднило бы поиск и увеличило бы неоднозначность формата файлов.

## ADR-012: Knowledge Wiki Layer через существующие адаптеры, не через интерактивный Claude Code (§35)

**Решение:** три новых воркфлоу (`Atlas - Wiki Ingest`, `Atlas - Wiki Query`, `Atlas - Wiki Lint`) реализуют паттерн RAW/WIKI/SCHEMA + ingest/query/lint (источник идеи — видео про подход Андрея Карпаты) поверх уже существующих `Atlas-OpenRouter Adapter Core`, а не через живую сессию Claude Code с прямым доступом к Anthropic, как показано в оригинальных видео. `Wiki Lint` вообще не использует LLM — только сравнение списков файлов.

**Почему:** видео предполагают безлимитный доступ к Anthropic из терминала — ровно та проблема, которую уже решает адаптерная архитектура (ADR-001) и история блокировки OpenRouter по IP РФ. Прогон рутинного обслуживания вики через уже оплаченные и проверенные агрегаторы не требует VPN/живого CLI-сеанса и не упирается в уже задокументированное ограничение (агент не может писать напрямую в прод n8n, §31).

---

## ADR-013: `Knowledge/` вместо новой папки `Wiki/`

**Решение:** новый слой вики использует уже существующую (но пустую) папку `Knowledge/`, а не отдельную `Wiki/`, как было предложено изначально 2026-08-17.

**Почему:** `Knowledge/` уже задокументирована в `README.md` как "заметки и конспекты" — заведение параллельной `Wiki/` дублировало бы назначение папки и противоречило бы принципу "не дублировать" (`PROJECT_PRINCIPLES.md`).
