> **Статус:** Фаза 0 — Проектное предложение  
> **Основа:** Архитектурный базис Second Brain + Atlas v0.3  
> **Версия документа:** 1.0 (23 октября 2026 г.)

## 1. Концепция и назначение системы

**AI-OS** — это персональная операционная система знаний и координации ИИ-агентов, построенная на модульном принципе:
1. **Слой данных и знаний (Second Brain):** Переносимая файловая база на базе Markdown, версионируемая в Git. Единый источник истины (Single Source of Truth).
2. **Слой автоматизации и исполнения (Atlas):** Движок на базе n8n, управляющий конвейерами данных, изоляцией провайдеров через адаптеры, вебхуками захвата и выдачи контекста.
3. **Слой взаимодействия агентов (Agent Interface):** Букмарклеты, файловые правила (`CLAUDE.md`, правила рабочей среды) и протокол передачи контекста (Handoff), позволяющие любой модели (ChatGPT, Claude, Gemini, DeepSeek, Antigravity) продолжать работу другой модели без потерь.

## 2. Ключевые компоненты архитектуры

### 2.1. Основной источник данных (Single Source of Truth)
* **Технология:** Структурированное файловое хранилище Markdown (Obsidian Vault).
* **Зачем нужен:** Текстовый формат гарантирует независимость от облачных провайдеров и вендоров софта. Любой ИИ-агент умеет читать и писать Markdown с нулевыми накладными расходами.
* **Что хранит:**
  * `Knowledge/`: Обобщённая база знаний, факты, синтезированные вики-страницы (`[[wikilinks]]`).
  * `Projects/<ProjectName>/`: Спецификации, проектные логи, архитектурные решения проектов.
  * `Projects/<ProjectName>/logs/`: Конспекты рабочих сессий и полные несжатые транскрипты диалогов (`-raw.md`).
  * `Courses/`: Обучающие материалы и конспекты курсов.
  * `Debates/`: Результаты автономных дебатов между ИИ-моделями.
  * `Templates/`: Шаблоны страниц и документов.
* **Можно ли обойтись на первом этапе:** **Нет.** Это центральное ядро всей системы.

### 2.2. Синхронизация и резервное копирование
* **Технология:** Гибридная трехуровневая схема:
  1. **Оперативная репликация:** Локальный клиент Яндекс Диска обеспечивает автоматическую синхронизацию рабочей директории `D:\YandexDisk\Atlas` с облаком Яндекса на случай аппаратного сбоя ПК.
  2. **Версионный бэкап:** Репозиторий GitHub (`takeprofit83/second-brain`). Коммиты происходят автоматически из n8n при захвате диалогов и вручную/полуавтоматически агентами.
  3. **Холодный архив артефактов:** Docker-контейнер MinIO (S3) на VPS для тяжелых бинарных файлов и дампов.
* **Можно ли обойтись на первом этапе:** Яндекс Диск и GitHub уже работают. MinIO на первом этапе опционален.

### 2.3. Управление версиями
* **Технология:** Git (GitHub, ветка `main`).
* **Зачем нужно:** Обеспечивает полную историю изменений, возможность отката поврежденных документов и аудит действий агентов.
* **Конвенция версионирования:**
  * Автоматические логи n8n: `auto: add conversation log ({timestamp})`.
  * Документация: `docs: update <file> (<reason>)`.
  * Кодовые инструменты: `feat: ...` / `fix: ...`.
* **Можно ли обойтись на первом этапе:** **Нет.** Необходим для предотвращения деградации контекста.

### 2.4. Формат проектной памяти и передача задач (Handoff Protocol)
* **Формат:** Каждый акт передачи контекста формирует стандартизированный Markdown-документ (согласно стандарту §25 Atlas):
  1. **Текущее состояние архитектуры/проекта:** версии, ID, пути к файлам, конфигурации.
  2. **Принятые решения и обоснование:** почему сделано именно так (с отсылкой к ADR).
  3. **Проверенные факты (Verified):** что уже проверено end-to-end.
  4. **Оставшийся план:** конкретные следующие шаги.
  5. **Ограничения и риски:** известные баги и нерешённые вопросы.
  6. **Скрытые секреты:** все пароли и ключи заменяются меткой `[REDACTED]`.
* **Передача задач между агентами:**
  * Из чата A (ChatGPT/Qwen/...) → Букмарклет захвата → n8n генерирует Handoff → коммит в `Projects/<name>/logs/`.
  * В чат B (Claude/Antigravity/...) → Букмарклет подхвата (Context Resume) или чтение последнего лога агентом → модель подтверждает контекст и переходит к следующему шагу.
* **Можно ли обойтись на первом этапе:** **Нет.** Без этого невозможна бесшовная передача работы.

### 2.5. Механизм поиска
* **Уровень 1 (Текущий, базовый):** Локальный поиск по файлам (`grep`, `ripgrep`, поиск Obsidian / VS Code). Детерминирован, бесплатен, мгновенен.
* **Уровень 2 (Спроектированный, среднесрочный):** Воркфлоу `Atlas - Wiki Query` в n8n — семантический поиск через LLM по оглавлению базы (`Knowledge/index.md`).
* **Уровень 3 (Перспективный):** Векторная база данных / эмбеддинги (pgvector в существующем Postgres на VPS) для RAG по всей базе знаний.
* **Можно ли обойтись на первом этапе:** Уровня 1 и 2 полностью достаточно. Векторную БД отложить до исчерпания простого поиска.

### 2.6. Интеграция с n8n (Оркестрация и AI-адаптеры)
* **Технология:** Экземпляр n8n в Docker (`https://n8n.neiroclone.ru`).
* **Роль:**
  * Приём сырых данных через вебхуки (`atlas-capture`, `atlas-docs-sync`, `atlas-wiki-ingest`).
  * Нарезка длинных текстов на части (Map-Reduce chunking) для обхода контекстных лимитов моделей.
  * Абстракция AI-провайдеров: Adapter Core принимает стандартный контракт `{ provider, system_prompt, user_input, model }` и обращается к Kie.ai, OpenRouter или Polza.ai.
  * Выполнение регулярных фоновых задач (Wiki Lint по крону).
* **Можно ли обойтись на первом этапе:** **Нет.** Движок n8n уже развернут и выполняет роль бэкенда системы.

### 2.7. Доступ через MCP / API / Файловые инструменты
* **Локальные агенты (Claude Code, Antigravity, Cursor):**
  * Доступ напрямую через файловую систему операционной системы. Это наиболее быстрый, надежный и прозрачный способ.
  * Поведение регламентируется файлом правил `CLAUDE.md` и проектными инструкциями в корне проекта.
* **Браузерные чаты (ChatGPT, DeepSeek, Gemini, Qwen):**
  * Доступ через Relay-страницу и букмарклеты захвата/подхвата (обход CSP браузера через W3C `postMessage`).
* **MCP-сервер (Model Context Protocol):**
  * Перспективный компонент. Нужен, когда агентам потребуется регламентированный API для вызова n8n-воркфлоу или структурированного поиска по Second Brain без сканирования всей файловой системы.
* **Можно ли обойтись на первом этапе:** Да, на первом этапе достаточно прямого файлового доступа и существующих вебхуков.

### 2.8. Безопасность и контроль прав
* **Принцип нулевого доверия к промптам:** Никакие пароли, SSH-ключи, API-токены не передаются в контекст внешних моделей. Промпты конспектирования обязуют заменять секреты на `[REDACTED]`.
* **Хранение секретов:** Локально — в защищенном хранилище KeePassXC (`atlas-secrets.kdbx`). На сервере — в закрытых credential-хранилищах n8n.
* **Сетевая изоляция:** n8n работает во внутренней Docker-сети за Nginx Proxy Manager с SSL-сертификатами. Вебхуки защищены заголовками `X-Atlas-Secret`.
* **Можно ли обойтись на первом этапе:** **Нет.** Это фундаментальное требование безопасности.

### 2.9. Защита от конфликтов при параллельной работе
* **Именование по таймстемпу:** Все новые артефакты и логи создаются с префиксом `{yyyyLLdd-HHmmss}-{source}-{chatId}`. Это исключает перезапись файлов при одновременной работе разных агентов.
* **Принцип дописывания (Append-only / Upsert):** Глобальные файлы (например, `index.md`, `log.md`) обновляются методом дописывания строк, а не полной перезаписи структуры.
* **Разделение зон ответственности:** Агент не модифицирует файлы другого активного проекта без явного указания пользователя.
