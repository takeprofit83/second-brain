# 1. Главный принцип: не общая память нейросетей, а единый источник правды

У разных нейросетей собственные механизмы памяти. ChatGPT не получает автоматически весь контекст Claude, Claude не видит автоматически переписку с ChatGPT, а новый чат не обязательно знает, что происходило в предыдущем.

Поэтому нам нужно создать внешнюю систему, доступную всем агентам.

Представь такую структуру:

**ТЫ → ЕДИНЫЙ ЦЕНТР УПРАВЛЕНИЯ → НЕЙРОСЕТИ → ОБЩАЯ ПАМЯТЬ**

Например, ты работаешь над сайтом.

1. ChatGPT анализирует задачу и предлагает архитектуру.
2. Claude Code вносит изменения в сайт.
3. У Claude заканчивается лимит.
4. Ты открываешь новый чат или переходишь к другой нейросети.
5. Следующий агент читает состояние проекта, изучает последние изменения и продолжает работу.

При этом тебе не приходится копировать десятки сообщений из старой переписки.

**Важный нюанс:** общая память не означает, что все нейросети автоматически обмениваются сообщениями. Мы организуем передачу контекста через общие файлы, инструменты и, при необходимости, автоматизацию.

# 2. Из чего я предлагаю построить систему

Я бы разделил её на пять уровней.

## Уровень 1. Общая память о тебе и правилах работы

Это информация, которая нужна практически любой нейросети независимо от проекта.

Например:

- Ты работаешь сразу с несколькими нейросетями.
- Предпочитаешь конкретные инструкции вместо длинных абстрактных планов.
- Не хочешь повторных тестов, если они расходуют платные кредиты.
- При доработке сайта необходимо сохранять существующую архитектуру и не переписывать то, что не относится к задаче.
- Если исправляется один элемент, остальные элементы должны оставаться нетронутыми.
- Нельзя считать задачу выполненной только потому, что агент написал код: результат необходимо проверить.
- Перед началом работы нужно изучить предыдущие решения и актуальные файлы.

Это твои постоянные рабочие правила.

Их не нужно переписывать в каждом чате.

Предлагаю хранить их в файле:

`USER_CONTEXT.md`

В нём будет только то, что действительно полезно разным агентам.

### Что в них хранить?

| `PROJECT.md` | Цель проекта, его устройство, основные требования |

# 3. Как сделать так, чтобы нейросети действительно пользовались этой памятью

Вот здесь начинается самое интересное.

Недостаточно создать папку с документами. Необходимо организовать доступ к ней.

Я вижу три варианта.

## Вариант А. Общая папка с файлами — самый простой старт

Создаём единую папку проекта, доступную тебе и используемым инструментам.

Она может находиться в репозитории сайта, в рабочей папке на компьютере или в другом общем хранилище.

Каждый агент получает инструкции:

1. Перед началом работы прочитать общие правила.
2. Прочитать описание нужного проекта.
3. Изучить состояние проекта и актуальные задачи.
4. Если задача касается кода, проверить реальное содержимое файлов.
5. После работы обновить состояние и подготовить передачу следующему агенту.

Например, Claude Code может использовать файл `CLAUDE.md`, а другие инструменты разработки — `AGENTS.md` или собственные инструкции.

В актуальной документации Anthropic описаны механизмы сохранения проектного контекста между сессиями через файлы инструкций и память: urlДокументация Claude Code о памятиturn0search2.

**Преимущества:**
- Простая реализация.
- Никакой сложной инфраструктуры.
- Контекст можно переносить между разными нейросетями.
- Ты контролируешь, что именно записано в памяти.

**Недостаток:** нужно обеспечить доступ каждого инструмента к этим файлам. Обычный чат в браузере не обязательно сможет самостоятельно прочитать папку на твоём компьютере.

Для первого этапа я бы выбрал именно этот вариант.

## Вариант Б. Общая память через MCP

Следующий уровень — подключить общую базу знаний через MCP.

MCP — это стандарт, позволяющий ИИ-инструментам взаимодействовать с внешними источниками данных и инструментами.

В нашем случае можно организовать сервер, который предоставляет агентам инструменты для работы с общей памятью.

Например:

- `search_memory` — поиск информации по всем проектам.
- `read_project` — чтение описания проекта.
- `get_current_state` — получение актуального состояния.
- `save_decision` — сохранение утверждённого решения.
- `update_task` — обновление задачи.
- `create_handoff` — подготовка передачи следующему агенту.

Представим, что ты пишешь новой нейросети:

«Продолжи работу над Dzen-studio».

Она обращается к общей памяти и получает:

- Цель проекта.
- Текущую архитектуру.
- Последние принятые решения.
- Список завершённых задач.
- Текущую задачу.
- Последние изменения и результаты проверок.

Не нужно каждый раз передавать всю историю вручную.

У Anthropic есть документация по организации постоянной памяти через инструменты и внешнее хранилище. В ней также описан принцип извлечения информации по мере необходимости, вместо загрузки всей базы в контекст каждого запроса: urlДокументация Anthropic по Memory Toolturn0search0.

Но есть важное условие: **каждый используемый агент должен поддерживать подходящий способ подключения к этому хранилищу**. Нельзя просто подключить MCP один раз и рассчитывать, что он автоматически появится во всех приложениях и обычных чатах.

## Вариант В. Полноценный центр управления ИИ-агентами

Это уже более серьёзная система.

Можно сделать собственную панель управления, в которой будут:

- Все проекты.
- Общая база знаний.
- Задачи и их статусы.
- История изменений.
- Используемые нейросети.
- Передача задач между агентами.
- Контроль версий файлов.
- История ошибок.
- Журнал принятых решений.

У тебя уже есть VPS с Ubuntu и Docker, а также опыт работы с n8n. Это даёт возможность впоследствии разместить часть такой инфраструктуры на собственном сервере.

Однако я бы не начинал с разработки большой системы. Сначала нужно отработать сам принцип передачи контекста, иначе мы рискуем потратить время на красивую панель, которая всё равно не решит проблему забытых решений.

# 4. Самое главное — протокол передачи эстафеты

Даже если у всех агентов общая память, необходимо установить единые правила завершения работы.

Я бы ввёл обязательный протокол.

### Когда агент начинает работу

Он должен:

1. Определить, над каким проектом работает.
2. Прочитать общую память.
3. Прочитать последние сведения о проекте.
4. Проверить текущую версию нужных файлов.
5. Уточнить, что именно требуется сделать сейчас.
6. Не менять уже утверждённые решения без необходимости.

### Когда агент заканчивает работу

Он должен записать:

- Что было сделано.
- Какие файлы изменены.
- Какие решения приняты.
- Что осталось незавершённым.
- Какие ошибки возникли.
- Какие проверки выполнены.
- Что следующему агенту нужно сделать первым.
- Как проверить результат.

И обновить `HANDOFF.md`.

Например, передача работы над сайтом может выглядеть так:

**Проект:** сайт услуг.

**Текущая задача:** доработка главного экрана.

**Выполнено:** изменена анимация смены текста.

**Изменённые файлы:** `index.html`, `styles.css`.

**Проверено:** анимация переключается на компьютере.

**Не проверено:** мобильная версия на реальном устройстве.

**Известная проблема:** индикатор анимации частично перекрывает текст на узком экране.

**Следующий шаг:** проверить мобильную версию и исправить позиционирование индикатора, не меняя остальную структуру блока.

**Ограничения:** не заменять изображение преподавателя, не менять шрифты остальных секций и не переписывать весь сайт.

Такой документ позволяет другому агенту продолжить работу, не повторяя уже выполненные действия.

Причём это особенно важно для тебя: ты неоднократно сталкивался с тем, что при локальном исправлении агент затрагивал другие элементы или возвращал ранее устранённые проблемы.

**Передача должна содержать не только задачу, но и запреты на повторение уже исправленных ошибок.**

# 5. Как не допустить, чтобы нейросети портили общую память

Есть одна серьёзная проблема.

Представь, что ChatGPT предложил архитектуру, Claude её изменил, а другой агент записал в память своё предположение, будто это окончательное решение.

Через несколько дней общая база окажется заполнена противоречиями.

Поэтому предлагаю ввести три категории информации.

| Категория | Что означает |
|---|---|
| **УТВЕРЖДЕНО** | Ты согласовал решение, и оно является действующим |
| **ПРОВЕРЕНО** | Результат фактически проверен, есть подтверждение |
| **ПРЕДЛОЖЕНО** | Агент предложил вариант, но решение ещё не принято |

Дополнительно полезно помечать устаревшие сведения.

Например:

```text
Решение: использовать текущую архитектуру сайта.
Статус: УТВЕРЖДЕНО.
Источник: согласование с пользователем.
Дата: 19.10.2026.

Предложение заменить архитектуру.
Статус: ПРОВЕРЯЕТСЯ.
Не применять без согласования.
```

Это особенно важно для сложных проектов, где обсуждение и реализация происходят в разных чатах.

Я бы также установил следующие правила:

- Агент не должен выдавать собственные предположения за утверждённые решения.
- Если два документа противоречат друг другу, нужно проверить актуальные файлы и историю изменений.
- Важные решения нельзя молча переписывать.
- Устаревшие инструкции нужно помечать, а не оставлять рядом с актуальными как равноправные.
- При передаче кода нужно указывать конкретную версию или состояние репозитория.

И ещё: **не нужно заставлять каждую нейросеть загружать всю информацию обо всех твоих проектах**. Это увеличивает расход контекста и затрудняет поиск нужного. Агент должен получать общие правила и только те сведения о проекте, которые нужны для текущей работы.

У тебя уже есть опыт с n8n, поэтому впоследствии можно автоматизировать почти весь процесс ведения контекста.

Представим такой сценарий.

### Сценарий 1. Создание проекта

Ты пишешь:

«Создай новый проект — автоматизация контент-производства».

Система:

1. Создаёт папку проекта.
2. Формирует шаблоны документов.
3. Сохраняет первоначальную цель.
4. Добавляет проект в реестр.
5. Создаёт список первых задач.

### Сценарий 2. Сохранение новых знаний

Во время работы агент принимает важное решение.

Например, вы выяснили, что конкретный API не поддерживает нужную операцию.

Вместо того чтобы через неделю повторять исследования, система сохраняет:

- Название сервиса.
- Что проверяли.
- Какой результат получили.
- Дату проверки.
- Ссылку на документацию или источник.
- Какие ограничения нужно учитывать.

При этом нужно различать проверенные факты, результаты тестов и предположения.

### Сценарий 3. Завершение сессии

Ты пишешь:

«Подготовь передачу следующему агенту».

Система формирует отчёт, обновляет состояние проекта и готовит краткий стартовый контекст для следующего чата.

### Сценарий 4. Запуск нового агента

Ты открываешь другой инструмент и выбираешь проект.

Он получает подготовленный контекст и инструкции.

Если инструмент поддерживает MCP или API, часть передачи можно автоматизировать. Если нет, система хотя бы сформирует готовый стартовый документ, который можно передать вручную.

### Сценарий 5. Поиск по всей базе знаний

Ты спрашиваешь:

«Мы уже решали проблему с мобильной анимацией на сайте?»

Система ищет по всем проектам и возвращает соответствующие решения, документы и результаты тестов.

Для этого не обязательно сразу создавать сложную векторную базу. На начальном этапе можно использовать обычные документы с хорошей структурой и поиск по ним.

# 7. Какой вариант я рекомендую именно тебе

Я бы не стал начинать с разработки полноценной мультиагентной платформы.

Тебе важнее получить работающий процесс, который не потребует постоянно обслуживать ещё один сложный проект.

Поэтому предлагаю двигаться в три этапа.

### Этап 1. Единая база контекста

Создаём:

- Общие правила работы.
- Реестр проектов.
- Шаблон описания проекта.
- Шаблон текущего состояния.
- Шаблон передачи работы.
- Единый формат хранения принятых решений.

На этом этапе уже можно переключаться между ChatGPT, Claude Code и другими агентами, не начиная работу с нуля.

### Этап 2. Автоматическое управление контекстом

Подключаем общую базу к инструментам, которые поддерживают интеграцию.

Для Claude Code настраиваем проектные инструкции.

Для других сред определяем их собственные способы чтения общих документов.

Добавляем автоматическое формирование передач и обновление состояния проектов.

# 1. Какой должна стать твоя система

Представь, что у тебя одновременно идут пять проектов: сайт услуг, Dzen-studio, AI-контент-фабрика, автоматизация дачи и KIS Reservoir Raid.

Ты работаешь над сайтом с Claude Code. Потом переключаешься на ChatGPT, чтобы обсудить стратегию. Через несколько дней возвращаешься к Claude.

Система должна обеспечивать следующее:

- ChatGPT знает актуальное состояние проекта.
- Claude видит утверждённые решения и последние изменения.
- Gemini или другой агент может подключиться без отдельной настройки всей базы знаний.
- Если агент обнаруживает новую информацию, он предлагает сохранить её в нужном месте.
- При завершении работы автоматически формируется отчёт.
- Следующий агент получает не всю переписку, а необходимый контекст.
- Если два агента изменили один файл, система обнаруживает конфликт.
- Ошибки, которые уже исправили, не приходится исправлять повторно.

При этом ты остаёшься главным: важные решения не должны приниматься только потому, что одна из нейросетей решила их изменить.

# 2. Самое важное: сделать память не просто файловой, а интеллектуальной

На мой взгляд, это ключевая часть проекта.

Обычная база знаний отвечает на вопрос:

> Где лежит информация о проекте?

Умная система должна отвечать на другие вопросы:

- Что сейчас происходит с проектом?
- Какие решения мы приняли?
- Почему выбрали именно этот вариант?
- Что изменилось с последнего раза?
- Какие действия уже предпринимались?
- Что не получилось и почему?
- Какие знания из других проектов применимы здесь?
- Что необходимо сделать дальше?

Для этого я бы организовал память в четыре слоя.

## Слой 1. Постоянные знания

То, что не должно теряться между сессиями:

- твой опыт и навыки;
- предпочтения в работе;
- общие правила взаимодействия с агентами;
- ограничения по инструментам и бюджету;
- принципы организации проектов.

Например, агент должен знать, что при доработке существующего сайта нельзя без необходимости переписывать его целиком.

## Слой 2. Память каждого проекта

У каждого проекта собственный контекст:

```text
Dzen-studio
├── Цель проекта
├── Архитектура
├── Технологии
├── Принятые решения
├── Текущие задачи
├── Ошибки и ограничения
└── История изменений
```

Такая же структура используется для остальных проектов, но состав документов может различаться.

## Слой 3. Оперативная память

Это то, что происходит прямо сейчас:

- текущая задача;
- активный исполнитель;
- последний успешный результат;
- незавершённые действия;
- ошибки;
- следующий шаг.

Именно этот слой нужен при переходе из одного чата в другой.

## Слой 4. Межпроектные знания

Это наиболее интересная возможность.

Допустим, ты решил определённую техническую задачу в Dzen-studio. Позднее аналогичное решение может пригодиться при разработке другого сайта.

Или ты разработал систему организации контента для подологии, которую можно применить в AI-контент-фабрике.

Система должна уметь находить такие связи.

Но здесь есть важное отличие от обычного поиска: **она должна предлагать применить найденное знание, а не автоматически переносить все решения из одного проекта в другой**.

Для этого можно начать с обычных связей между Markdown-документами, а затем добавить семантический поиск по смыслу.

# 3. Как сделать автоматическую передачу работы между нейросетями

Я бы не ограничивался файлом `HANDOFF.md`, который агент должен вручную заполнять в конце каждого чата.

Нам нужна система состояний задач.

Например:

```text
НОВАЯ ЗАДАЧА
     ↓
АНАЛИЗ
     ↓
В РАБОТЕ
     ↓
ОЖИДАЕТ ПРОВЕРКИ
     ↓
ПРОВЕРЕНА
     ↓
ЗАВЕРШЕНА
```

При этом возможны дополнительные состояния: заблокирована, ожидает твоего решения, обнаружен конфликт.

### Как это будет работать

Допустим, ты поручил Claude Code исправить мобильную версию сайта.

**Шаг 1.** Система загружает контекст проекта и создаёт задачу.

**Шаг 2.** Claude изучает актуальные файлы, предыдущие решения и ограничения.

**Шаг 3.** После выполнения он сообщает, что изменил, и сохраняет результаты.

**Шаг 4.** Система проверяет, обновлено ли состояние проекта, и фиксирует результаты доступных тестов.

**Шаг 5.** Задача переходит на проверку.

**Шаг 6.** Другой агент получает задание проверить мобильную версию, не переписывая уже сделанное.

**Шаг 7.** После проверки система сохраняет итоговый результат и обновляет контекст.

Ты можешь продолжать общаться с нейросетями как обычно. Внутренняя система будет отвечать за сохранение состояния и передачу задач.

Однако есть нюанс: если Claude Code или другая нейросеть завершает работу неожиданно, автоматизация не всегда сможет получить отчёт из её чата. Для надёжности важные изменения следует сохранять по мере выполнения, а не только при завершении сессии.

# 4. Что я бы поручил n8n

У тебя уже есть опыт работы с n8n, поэтому нет необходимости создавать собственный оркестратор с нуля.

Но я бы не делал один огромный workflow, отвечающий за всё.

Лучше создать несколько независимых процессов.

### Процесс А. Обновление контекста проекта

Запускается после существенных изменений.

Он:

1. Получает сведения о завершённых действиях.
2. Проверяет, какие документы проекта нужно обновить.
3. Формирует предложения по изменению контекста.
4. Сохраняет подтверждённые изменения.
5. Фиксирует результат в Git.

### Процесс Б. Передача задачи

Он:

1. Получает задачу и её текущее состояние.
2. Формирует пакет контекста.
3. Указывает ограничения.
4. Фиксирует ожидаемый результат.
5. Подготавливает передачу следующему агенту.

### Процесс В. Поиск знаний

Ты задаёшь вопрос:

«Мы уже решали подобную проблему с API?»

Система ищет в документах и, если потребуется, в индексированной базе знаний.

В результате ты получаешь найденные решения, источники и ссылки на конкретные документы.

### Процесс Г. Контроль целостности

Он проверяет:

- Какие проекты давно не обновлялись.
- Какие задачи зависли.
- Есть ли незавершённые передачи.
- Не расходятся ли актуальные документы с состоянием репозитория.
- Есть ли незафиксированные изменения.

При необходимости система уведомляет тебя.

**Важное ограничение:** n8n не получает автоматически доступ ко всем чатам всех нейросетей. Для каждой интеграции необходимо отдельно определить доступный механизм: API, MCP, события, файловые операции или другой способ взаимодействия.

Поэтому мы будем автоматизировать прежде всего те этапы, для которых реально доступен надёжный интерфейс.

# 5. Нужна ли нам отдельная база данных?

Не обязательно на первом этапе.

Я бы не стал сразу устанавливать PostgreSQL, Redis, векторную базу и ещё несколько сервисов.

Сначала можно использовать Markdown-файлы как основное хранилище знаний, а Git — для контроля версий.

Когда станет понятно, какие данные нужно искать и обновлять автоматически, можно добавить базу данных для оперативного состояния задач.

Например:

| Тип информации | Где хранить |
|---|---|
| Описание проектов | Markdown |
| Постоянные инструкции | Markdown |
| Принятые решения | Markdown |
| Код проектов | Git |
| История изменений | Git |
| Текущие состояния задач | Сначала Markdown, позднее при необходимости БД |
| История автоматизаций | n8n и его хранилище |
| Индекс для семантического поиска | При необходимости отдельное хранилище |

Так мы не будем дублировать одну и ту же информацию в нескольких местах.

## 2. С чего начнём

Предлагаю три этапа.

**Этап 1. Установка Obsidian и подключение существующих знаний.**

## 4. Одно архитектурное решение, которое я хочу зафиксировать заранее

Obsidian хранит заметки в виде обычных Markdown-файлов в локальной папке — это позволяет другим программам работать с ними напрямую. Поэтому мы сможем использовать существующие инструменты, не привязывая всю систему к одному приложению. <Cite refs={["turn706134search14","turn706134search9"]}/>

Но я не рекомендую делать так, чтобы все нейросети бесконтрольно редактировали одну и ту же базу одновременно.

Вместо этого организуем три уровня доступа:

- **Чтение:** агент может искать и получать контекст.
- **Предложение изменений:** агент подготавливает новые знания и обновления.
- **Запись подтверждённых изменений:** система сохраняет их, фиксирует версии и разрешает конфликты.

Для безопасных операций можно будет постепенно включать автоматическую запись. Для критичных изменений — сохранять подтверждение и возможность отката.

Это позволит добиться высокой автоматизации без ситуации, когда один агент незаметно переписывает решения другого.

**Твой следующий шаг сейчас один:** запусти в Antigravity фазу 0 по заданию выше. Не нужно пока устанавливать Obsidian, создавать MCP-сервер или менять конфигурацию VPS. Сначала получим реальную картину твоей инфраструктуры и на её основе спроектируем конкретную реализацию.

Пользователь: Фаза 0 (**Аудит и проектирование системы AI-OS**) завершена. Никаких изменений в боевую инфраструктуру, установок пакетов или коммитов в Git не производилось.

Сопоставление требований архитектора с проектом показало: **у вас уже есть работающий и зрелый фундамент (Atlas v0.3 + Second Brain)**. Система AI-OS не создаётся с нуля, а органично вырастает из текущих наработок.

### 1. Яндекс Диск или Yandex Cloud?

Здесь важно различать три разных компонента:

Не нужно подключать дополнительные облачные сервисы, пока не установлено, какие задачи уже решает имеющаяся инфраструктура.

### 2. Нужен ли Obsidian?

Я бы выбрал **Obsidian как удобный интерфейс к Second Brain**, если твоя текущая база уже хранится в Markdown и её структура совместима с Obsidian.

Но важно понимать: Obsidian не должен становиться ещё одной отдельной базой, которую приходится синхронизировать с Second Brain. Это приложение для работы с файлами, а не дополнительный источник истины.

Моя предлагаемая схема:

- **Second Brain** — существующая база знаний и проектов.
- **Obsidian** — удобный интерфейс для чтения, редактирования и связывания заметок.
- **Git** — история изменений и контроль версий.
- **Яндекс Диск** — если он уже используется, синхронизация файлов в рамках проверенной схемы.
- **n8n** — автоматизация передачи контекста и взаимодействия между компонентами.

При этом устанавливать Obsidian прямо сейчас необязательно. Сначала нужно посмотреть на структуру существующего Second Brain, чтобы не создать дубликаты и не сломать уже работающие процессы.

Адаптеры Atlas могут позволить менять провайдера, не перестраивая всю автоматизацию. Но сначала необходимо убедиться, что существующий Adapter Core действительно поддерживает единый контракт, обработку ошибок, тайм-ауты и учёт стоимости.

## 5. Как поймём, что Фаза 1 действительно удалась

Не по количеству созданных файлов и не по красивой архитектурной схеме. По реальному тесту:

- Открываем новый чат в ChatGPT и получаем контекст выбранного проекта.
- Передаём его в Claude или другой ИИ.
- Новый ИИ правильно называет текущее состояние, последние подтверждённые решения и следующий шаг.
- Контекст другого проекта не подмешивается.
- Система не раскрывает секреты.
- Повторный запрос не создаёт дубликаты.
- Неудачный запрос или конфликт версий не повреждает исходные данные.

Когда этот сценарий заработает, можно будет переходить к автоматическому сохранению результатов работы и дальнейшей интеграции.

**Моя рекомендация:** сначала добиться надёжного восстановления контекста в один клик. Именно это превратит Second Brain и Atlas из набора полезных инструментов в систему, которая действительно помогает тебе бесшовно работать между разными ИИ. memcite
